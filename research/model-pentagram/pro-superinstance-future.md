## 1. THE BOUNDARY OF EQUILIBRIUM-BASED COMPLETION

### What the Spectral Gap Model Cannot Do — A Formal Trade-off

The fleet-jobs protocol and its spectral gap completion criterion form an **equilibrium-based model**: a computation is "complete" when the coupling matrix of agent-task assignments reaches a stable eigenstate — empirically, when the spectral gap (λ₂ − λ₁) crosses a threshold, indicating no agent wants to reassign. This is an *ergodic* model of computation: work completes when the system thermally equilibrates.

**The formal trade-off is this: equilibrium models capture *convergence* but cannot prove *correctness*.**

Specifically, the spectral gap model is fundamentally incompatible with the following computation types:

### A. Non-ergodic Computations (Stateful Protocols)

Any computation with **irreversible state transitions** violates the assumptions of the spectral gap model:

- **Cryptographic operations** (signing, verification, key derivation) — these involve discrete, irreversible state changes. A task queue signing a message cannot be "close enough to complete." Either the signature exists or it doesn't. The spectral gap cannot distinguish a correctly formed signature from a near-miss.

- **Ordered multi-stage pipelines** — where stage N+1 depends on stage N producing a *correct* result, not just *a* result. The spectral gap model can detect that agents have stopped reshuffling (equilibrium), but it cannot verify that Stage 1's output satisfies Stage 2's preconditions.

- **Transactional operations** (atomic commits, ledger entries) — these require all-or-nothing guarantees. The spectral gap equilibrium tells you the system has settled, but it cannot tell you that a partially-executed transaction was rolled back correctly.

### B. Non-Commutative Operations

The spectral gap model implicitly assumes commutativity of task completion — agent A completing task X, then agent B completing task Y, should yield the same end state as B→A. But:

- **Database migrations** require strict ordering. Migrate to schema v2 before inserting v2-format rows. The spectral gap cannot model this dependency ordering.

- **Deployment rollouts** — canary → full → smoke test. The order of completion matters, and correctness demands traceability of the rollout graph, not just equilibrium.

- **Conflict resolution** (merge commits, concurrent edits) — whether two agents' outputs conflict is a *semantic* question, not a spectral one. The gap can tell you agents stopped disagreeing; it cannot tell you their consensus is correct (or that a third merge was needed, silently skipped).

### C. Negative-Result Computations

The spectral gap model detects *presence* of completion (agents stop moving), but it cannot detect:

- **Absence of failure** — a task that should have errored but silently hung is indistinguishable from a slow-completing task. The spectral gap converges in both cases.

- **Intentional non-completion** — a task that requires an explicit "no" (security audit signoff, approval gate) produces the same spectral signature as a task nobody got to yet.

- **Malicious convergence** — if agents collude to produce a wrong-but-agreed-upon result, the spectral gap will converge happily. The model has no notion of *truth*, only *agreement*.

### D. Formal Boundary Statement

```
A computation C is spectral-gap-computable iff:
(1) C's correctness criterion is reducible to a fixed-point of agent-task assignments,
(2) C's state space has a unique equilibrium reachable via monotonic progress,
(3) No sub-computation of C requires semantic verification of intermediate results.

Equivalently: the spectral gap model operates in the space of 
*collective behavior*, not *individual correctness*.
```

## 2. ONE FUTURE: PROOF-CARRYING FLEET

Given 1,584 repos and 5 active agents, the path that *maximizes formal guarantees* is not better spectral gap measurement — it's abandoning the equilibrium model altogether for **proof-carrying computation**.

### The Architecture

Every computation (job, task, sub-task) in the fleet produces, along with its output, a **verifiable proof of correctness**. This is the SuperInstance fleet as a *distributed theorem prover*.

**Layer 1: Per-Crate Proof Stamps**

Each agent, upon claiming a task, receives not just the task spec but a **proof obligation**: a formal statement of what "correct completion" means. The agent executes and produces:
- The output artifact (code, data, deployment)
- A **proof certificate** (a machine-verifiable attestation that the output satisfies the obligation)

These proofs are not hand-written. They are generated by:
- **Type-checked deps** (for package management: cargo-semver-verification on crate updates)
- **Model-checked state transitions** (for deployment: KLEE-style symbolic execution on stateful operations)
- **Zero-knowledge succinct proofs** (for expensive verification: zkSNARKs compressing months of symbolic execution into milliseconds of verification)

**Layer 2: Fleet History as a Proof Chain**

The fleet registry becomes a **blockchain of proofs**, not just a log of assignments:
```
block N = {
    tasks: [(job_id, output_hash, proof_hash, prover_agent)],
    state_root: h(previous_state + tasks),
    proof_root: h(all_proofs_in_block)
}
```

Any agent can verify any historical computation by:
1. Fetching the proof certificate from the registry
2. Running the verifier on the output artifact + proof
3. Checking the proof root commitment

**Layer 3: Third-Party Verifiability**

This is the crucial jump: a fleet audit (by a human, by an external CI, by a regulator) requires **zero trust in fleet agents**. The auditor needs only:
- The output artifact
- The proof certificate
- The verification key (one-time setup)

No re-execution needed. No access to the fleet's internal state. The proof is self-contained.

### What This Enables

- **1,584 repos can now be CI-verified without CI**: a single verifier script checks all crate proofs in O(N) time, not O(N * execution_time).
- **Agent reputation becomes measurable**: proofs vault tracks proof-valid vs proof-invalid submissions. An agent with 100% valid proofs is trusted; one with 95% gets auditing. This replaces spectral trust with *probabilistic-certain trust*.
- **Fork-resistant deployments**: any forked repo that claims to match upstream must produce a proof of behavioral equivalence. No proof → fork detection.

## 3. THE VERIFIABILITY GAP

### Why the Spectral Gap Might Be Wrong

The core problem: the spectral gap is a *heuristic* for equilibrium, not a *certificate* of correctness. The gap can converge to a false positive in several ways:

**Failure Mode A: The Null Equilibrium**

```
Scenario: A fleet with 3 agents, 10 tasks.
- Agent A takes tasks 1-4, Agent B takes 5-7, Agent C takes 8-10
- Agents stop reshuffling → spectral gap converges
- Reality: Agent C's tasks 8-10 are all blocked on a shared resource
  that Agent C doesn't hold. Agent C hasn't touched them.
  The system is *stable* but *incomplete*.
```

The spectral gap cannot distinguish "everyone finished" from "everyone got stuck but stopped complaining."

**Failure Mode B: The Ghost Task**

A task that doesn't make it into any agent's queue (dropped on write, lost in transit, never read). The coupling matrix never includes it. The spectral gap converges to a steady state that *looks* like completion but silently dropped work. This is a fundamental completeness gap — the spectral gap measures *assigned* work, not *intended* work.

**Failure Mode C: The Bad Consensus**

Two agents both claim completion of task 17 with different outputs. The spectral gap sees "task 17 completed" twice but doesn't notice outputs disagree. The task is marked done with arbitrary whichever result the registry stored last. No violation of spectral convergence.

### The Falsification Test for Fleet-Jobs Protocol

A falsification test exposes a mismatch between a model and reality. For the fleet-jobs protocol, the test is:

**The Fork Test:**
```
Given: 5 identical agents, 1 identical task (build & sign a crate)
Protocol: assign to any willing agent
Check: spectral gap ≤ threshold at t=0
Then: at t = threshold_time, inspect all 5 agents' output
Falsification condition: 
  Any two agents have output that disagrees on the crate's hash
  OR any agent's output is missing
  OR any agent's output fails the build

If falsification condition holds at spectral convergence:
  → The spectral gap falsely signaled completion
```

This test exposes a fundamental gap: the spectral gap is an *agent-level* property (have they stopped moving assignments?) but the correctness question is *object-level* (is the output correct?). These live in different formal domains.

**The Falsification Statement:**

```
∀ fleet F, ∀ job set J:
  spectral_gap(F) ≤ ε ∧ completeness_check(J) = ❌
  → fleet_jobs_protocol(J) is NOT a sound verification technique

Where completeness_check(J) is any third-party verifiable 
assertion about J's outputs.
```

This is a theorem we can prove by counterexample: construct an F and J where the spectral gap converges to ε but the outputs are wrong/incomplete. The fork test above is one such construction.

## 4. THEOREM SKETCH: VERIFIABILITY AS COUPLING

**Theorem (Verifiability-Coupling Duality).**  
*Any fleet operation that can be verified by a third party can be expressed as a coupling matrix computation.*

**Interpretation.**  
Third-party verifiability and coupling-matrix equilibrium are *duals* — every verifiable computation corresponds to some equilibrium checking, and every equilibrium state can be verified by checking spectral properties.

**Proof Sketch.**

Let a fleet operation O consist of:
- A set of agents A = {a₁, a₂, ..., aₙ}
- A set of tasks T = {t₁, t₂, ..., tₘ}
- An assignment relation R ⊆ A × T (agent a_i is assigned task t_j)

**Forward direction (Verifiability → Coupling).**

Suppose O can be verified by a third party V. V has access to the outputs of O but not the internal state of the fleet. The verification procedure is an algorithm V(outputs) → {true, false}.

Construct a coupling matrix C where C[i][j] = 1 if agent a_i claims completion of task t_j, and 0 otherwise. The equilibrium state of C is the fixed point of assignment reshuffling — the point at which no agent would gain by reassigning.

The key insight: any verification procedure V that is *monotone* (verifying more outputs never invalidates previously verified outputs) corresponds to checking that C is in equilibrium and that all entries match a reference coupling matrix C* (the ground truth of completed tasks). 

Formally: there exists a coupling matrix C* (derivable from V's verification predicate) such that:
- V(outputs) = true ⟺ C = C*
- C* is a spectral-equilibrium matrix of the fleet-jobs protocol

Because V's monotonicity ensures that any deviation from the reference equilibrium is detectable as increased spectral rank (unstable agents wanting to move).

**Reverse direction (Coupling → Verifiability).**

Conversely, given a coupling matrix C in spectral equilibrium, define a verification procedure V_C as:

1. For each agent aᵢ with assigned tasks Tᵢ = {tasks where C[i][j] = 1}:
   - Request the output artifact and proof certificate from aᵢ
   - Verify that the output hash matches aᵢ's claimed completion in C
2. Verify that the set of all claimed completions is a valid solution to the fleet's assignment problem (tasks partition, no double-booking, etc.)

This V_C is a third-party verifier: it only reads outputs, not fleet internals. And V_C returns true iff C is in equilibrium and the outputs match the claims.

**Corollary (The Spectral Completeness Bound).**

The spectral gap ε at which C converges bounds *verification soundness*: any third-party verifier that accepts spectral-gap-converged matrices must tolerate false positives at rate proportional to ε. Specifically:

```
P(false_positive | ε) = O(ε · n · m)
```

where n = agents, m = tasks, and ε is the spectral gap threshold.

**Corollary 2 (Proof-Carrying Elimination of ε).**

With proof-carrying computation, the spectral gap ε becomes irrelevant — the verification procedure checks proofs directly, not equilibrium. The coupling matrix C becomes a *coincident* structure: it happens to record the assignment, but correctness flows from the proofs, not from C's spectral properties. The duality theorem still holds (verifiability ≈ coupling), but the coupling matrix is *referential* — it references proofs, not just claims.

**Practical Implication.**

The current spectral-gap model is *sound* for detecting system stall and *complete* for detecting assignment completion. But it is neither sound nor complete for detecting *correct computation*. To bridge this gap, the fleet must shift from:

```
Equilibrium-based:  "the work is done when agents agree it's done"
```

to

```
Proof-based:  "the work is done when we can prove it's correct"
```

The duality theorem assures us these are not competing models — they are *dual representations* of the same verification structure. The shift is from implicit verification (spectral gap) to explicit verification (proof certificates). The coupling matrix remains the canonical representation; we only change what fills its entries: from "assigned" to "verified-with-proof."

## APPENDIX: Formal Notation

**Spectral Gap.** λ₂(C) − λ₁(C), where λ₁ ≤ λ₂ ≤ ... ≤ λₙ are the eigenvalues of the coupling matrix C (normalized Laplacian of the agent-task bipartite graph).

**Equilibrium.** C is at equilibrium when spectral_gap(C) ≤ ε for a fixed threshold ε > 0.

**Completeness.** A fleets job J is *complete* when there exists a C in equilibrium such that C encodes J's assignment and all outputs are valid.

**Soundness.** A verification procedure V is *sound* if V(outputs) = true ⇒ outputs satisfy J's specification.

**Completeness.** V is *complete* if J's outputs satisfy J's specification ⇒ V(outputs) = true.

**Spectral Soundness Theorem (to be proved).**  
The spectral gap model is *not* a sound verification procedure for arbitrary computations. Soundness holds only for the restricted class of ergodic, monotone, commutative computations. For all others, proof-carrying computation is required.
